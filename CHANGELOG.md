# Changelog

All notable changes to OhMyRASP are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Security
- On a request with a body (one the agent recorded, a form or multipart body the container parsed, or an operation carried from such a request), every agent line builds the event, and the primary its block exception and block page, from an allow-list instead of removing body text by string matching: the rule id, category, action and hook, a fixed message made from the rule id, the details that are a rule's own constants, the one input field the finding matched with its value cut to 256 characters (a URL in the name or the value without its credentials, and the marker alone as the value of a field whose name holds a credential's name, such as `password` or `user[token]`), and every other operand only as its kind and length (`command, 23 chars`); the request without its parameters. Matching missed body text a sink had transformed (case-changed, percent-decoded, cut, joined, one or two characters long). A hook failure on such a request reaches error telemetry by its exception class alone. Events on requests without a body are unchanged. [Request bodies](docs/detection.md#request-bodies)
- A detection's details no longer carry the credentials of a URL. Every agent line removes the user information, Oracle's `user/password@`, and the value of each credential-named parameter (in the query, the fragment and a JDBC URL's `;` properties) from every URL in a detection's details before writing or uploading it, and the MySQL rule records the driver, host and options instead of the URL. Before, a JDBC URL a pool configured, with its password, reached the spool and the cloud when the rule reported it, in log-only mode too. On a request with a body the details are the allow-list above, whose one field name and value get the same redaction; a `;` is part of a URL's user information except in a JDBC URL; the MySQL rule's host is the one Connector/J connects to and never the `(user=...)(password=...)` keys of its `address=` form, in the spool, the primary's block exception and the direct-cloud upload alike.
- A failure while the primary Java agent makes a block's evidence safe (redaction, body scrubbing, recording) no longer lets the operation run: the block starts from the finding without its evidence and every step that reads the evidence runs inside the protected region. Before, the fallback was built before it, so a failure there was taken for a detector failure and the operation continued.
- The host daemon's console has no authentication: whoever reaches its socket can change `mode` and `outside_request`. It binds to loopback by default; the daemon README now says who that lets change control and how to expose it. [Daemon README](daemon/README.md)
- The primary Java agent redacts the values of sensitive parameters inside the `request.query` string of an event line, with the marker it already used for `parameters`. The query is split on `&` only (a `;` stays inside its piece, as Tomcat reads it, so `password=alpha;omega` is redacted whole), and a piece is redacted when it, or what it decodes to (percent escapes and `+`, up to 8 rounds; a piece still changing after that counts as sensitive), holds a sensitive parameter name as a token: `id=1&amp;password=x`, `%2570assword=x`, `user[password]=x`, `cfg={"password":"x"}` and `next=/cb?token=x` are all redacted, and `passwordless=1` is not. A search such as `q=password+policy` is redacted too: the rule reads tokens, not intent. A query longer than 8192 characters is not scanned and is replaced by the marker as a whole. Before, `password=...` in a query string was written to the spool, shown in the local console and uploaded by the daemon (and by the direct-cloud client) as written.

### Fixed
- Every agent line now sees the XMLDecoder elements `<method>`, `<property>` and `<new>`. The XMLDecoder rules (`xml_decoder_runtime`, `xml_decoder_webshell`; on Java 8, 11 and 17 `xml_decoder_runtime_execution`, `xml_decoder_script_file_write`) watched only `<object>` and `<void>`, which run as `java.beans.Expression` and `Statement`; the other three call their method or constructor directly. So `<object class="java.lang.ProcessBuilder">...<method name="start"/></object>`, or `Runtime.exec` reached through `<method>`, started its process with no finding, inside a request or not, and `<new class="java.io.PrintWriter">` on a `.jsp` path was stopped only by the file-write rule. Each of these elements is now classified, before it calls, the way `<object>` and `<void>` are, and a block stops the document. `<field>` is still not observed: a field read or write runs nothing by itself. [XMLDecoder object graphs](docs/detection.md#xmldecoder-object-graphs)
- The backport agents (Java 8, 11 and 17) turn their hooks on only when a start commits, after its start line is written, as the primary does. Before, a hook acted as soon as the runtime started, while the transformers were still being registered, and when the start then failed an application thread already inside a hook could get an `IllegalStateException` from the agent. A second start in the same JVM (an `agentmain` after `premain`, an entry called directly) now fails and touches nothing; before, it registered every transformer a second time. A start that failed leaves the runtime's settings readable, so a hook that was running finishes without throwing.
- The JVM's exit no longer waits on a stalled event output on any agent line. The shutdown hook writes nothing itself and holds no lock while it waits: the hook-miss report gets up to 500 ms, then the event writer thread drains the queue for up to 2 seconds, and what it has not written by then is dropped and counted. Before, the hook wrote the rest of the queue itself and could hang in the file's open or append (on the backports while holding the start lock). An event submitted after the exit began is now dropped and counted instead of written on the submitting thread (sync mode and console targets still write inline).
- A hook-miss line can no longer delay or cost a detection. It never takes the detections' write lock and is appended to the spool on the report's own thread as one write; on a console target (`stderr`, `stdout`) it is now dropped and counted, because it would share the stream the detections are printed to. Before, a diagnostic stalled in its open or append held the lock every detection write waited for. Each detection batch is now one write too, so lines never interleave.
- The backport agents write every spool line as UTF-8, whatever the JVM's default charset. Before, detections and the start line used the default charset while diagnostics used UTF-8, and the daemon reads UTF-8.
- The primary agent's warm-up at start reports to a logger that writes nothing on its own thread only, and stops when the start stops waiting for it. Before, it swapped the process-wide reporter, and a warm-up still running after its timeout could report through the real logger or keep acting once the hooks turned on.
- With `cloud_direct=true`, a policy the primary agent's cloud client fetched is no longer installed after the client was closed (a failed start), and a stopped runtime installs none. A failure to start cloud reporting after the commit, even with a broken `stderr`, no longer makes the launcher report a failed start with the hooks on.
- The primary agent's undo of a failed start stops its own threads before it retransforms classes back, which can run other agents' transformers; and a detection batch waiting for the write lock when the start failed is no longer written.
- The request-body read rewrite no longer makes a valid class fail verification. It added a branch and a stack map frame with every local unset inside the original read method; when the method's own handler covered that point and used `this` or a local (a valid `synchronized` read built so), the JVM rejected the class (`VerifyError` on JDK 25), which breaks the container stream it rewrites. The entry and each return now call the hooks straight-line, and one handler entered last in the exception table releases the recorder and rethrows the same throwable object; the hooks' own code catches every failure but the line's block. The `hook-targets` probe now defines and verifies every class a hook rewrites in the recorded library JARs, on each JDK.
- A request's body belongs to the stream whose read first returns data: an unrelated read that throws, returns nothing or ends first no longer takes it. A distinct request dispatched inside another one gets its own body recorder until it leaves; a block latched on a body is thrown only by reads of that body's stream outside the agent's own inspection; an inner read that throws no longer releases the outer read's claim.
- A body state counts as decided only once its evaluation completed or blocked, body findings are suppressed only against the finding the servlet entry actually reported, and a request's body states cause at most `RequestBody.MAX_EVALUATIONS` rule evaluations. A merged-inputs cache made from a body state can no longer be published into a request context after its dispatch ended. The H2 console exemption reads request parameters only, not body fields.
- A primary Java agent start that fails no longer leaves active hooks in classes it already rewrote. Removing a transformer does not take injected calls out of a class, so a class rewritten while the start still ran (an application thread loading it meanwhile) kept blocking and logging after the launcher reported `ohmyrasp-agent-start-failed`. Every hook entry now reads one flag that turns on only when the start commits, and a failed start leaves it off: those calls do nothing. A real-JVM test fails a start after `javax.naming.InitialContext` was rewritten and checks that a remote JNDI lookup then fails as it does without the agent; before, it was blocked.
- The primary agent starts once per JVM even when its bootstrap entry is called directly, bypassing the launcher: a second or concurrent start fails and touches nothing. Before, it could register a second transformer and replace the cloud client while the first start's hooks ran.
- A primary start from a shutdown hook fails before it starts anything. Before, the event logger's class failed to initialise (its shutdown hook was refused in its static initialiser), the undo could not reach it, and its writer thread was left running.
- The primary agent's undo of a failed start stops the event writer without writing or waiting on its output (a writer stuck on a full pipe is left to finish that call), stops the control-file poller before it returns (a poll in progress no longer changes the control state afterwards), and runs each step on its own, so one failing step no longer skips the rest.
- With `cloud_direct=true`, the primary agent sends nothing to the cloud (registration, heartbeat, policy fetch) and does not replace the JVM's default handler for uncaught exceptions until its start has committed, so a failed start has made no cloud request and leaves the application's handler as it was.
- An attach of the primary agent after the application used the agent JAR's hook classes from its own class path now fails, naming the class and its loader, as on the backports. Before, the start succeeded while the application's classes called a copy of the hooks that never acted.
- The primary agent no longer initialises `InetAddress` while it starts: an application that sets `jdk.net.hosts.file` or the address-cache security properties in code now has them applied, as without the agent.
- The hook-miss report's worker thread is created when a start commits, on the start's own thread, without inheriting its inheritable thread-locals, instead of on the class-loading thread of the first miss, where creating a thread could run an application's `childValue` under a class-loading lock. It is a daemon thread that lives as long as the JVM. A failed start on any line drops what it queued and creates no worker (the Java 8, 11 and 17 undo now turns the report off), and at exit the event writers give the worker up to 500 ms to hand over a line before they drain.
- The hook-miss report no longer runs inside the transformers' ASM chain: after a class is transformed, one separate pass reads the finished class and matches each hooked method by name, descriptor and the agent method it should call (directly or through the reflective sequence the hooks emit), so a call in another method or overload no longer hides a miss, and nothing the check throws (including `StackOverflowError` or `OutOfMemoryError`) changes the bytes a transformer returns. A queued miss keeps only a few bounded strings (the methods found, at most 16 with a `found_omitted` count, and the location without query, fragment or credentials, read from the URL's own fields), never the class file, its protection domain or its loader, so a stalled report cannot keep an undeployed application in memory; the 32-line limit is charged when a miss is queued. An exempt older library version no longer uses up the pair before a broken one loads, and a backport transformer that throws is reported as `transform_failed`. The table is read only from the agent's own JAR (at most 1 MiB) and used only when it names its family and ends with a matching row count and SHA-256; otherwise the line starts with the report off and prints one `hook-miss report unavailable (protection is not affected)` line. A diagnostic line never takes a detection-queue slot or shares a detection batch: it waits at most 100 ms for the write lock and is dropped and counted (`JsonEventLogger.diagnosticsDroppedCount`, `HookMisses.sinkFailures`) when the lock stays busy, the writer is closing, not started or cancelled, or the write fails; text is cut on a code point boundary with unpaired surrogates replaced; a file target no longer mirrors it to the console. The manifest of a JAR is read under the agent's own-I/O mark and only for a JAR up to 256 MiB with a manifest up to 64 KiB (`implementation_version` is omitted otherwise). The list members `looked_for_omitted` and `found_omitted` replace the `... N more` list element. [Hooks that did not apply](docs/agent.md#hooks-that-did-not-apply)
- The host daemon treats a record with an `algorithm` and an `action` as a detection whatever `event` or `"kind":"diagnostic"` marker it also carries (an explicit `"kind":"detection"` still wins, and an agent start line stays a lifecycle line), so a detection whose escaped data contains a reserved string is recorded and uploaded again. It keeps one hook-miss entry per unit, class and code identity (path and version) instead of per file name, counts `hook_misses_dropped` in lines and warns once at the first suppression line.
- The host daemon kept the cloud's `outside_request` and the host's override in one field: withdrawing the policy, or replacing it with one without the setting, left the cloud's `log` in force, an unchanged policy kept a host override and an unrelated policy edit overwrote it. The cloud's value now stays inside the policy and the host's is its own member. The daemon no longer writes `block` when nothing set the member (which overrode an agent started with `log`), keeps a hand-edited value nobody accepts as found instead of rewriting it as `block`, and reads a member named twice with its last value, as the agents do, instead of reinitialising the document. The host dashboard re-reads mode and `outside_request` on every refresh; it applied them only on its first load.
- The optional direct-cloud client of the primary agent (`cloud_direct`) runs its requests as the agent's own I/O, so a backend address that matches a network rule no longer stops registration, heartbeats or uploads, and the policy it installs applies its `outside_request`.
- Saving an unrelated hardening setting of an environment on the console's Protection page no longer pins the `outside_request` it inherits from the application: the settings API reports inherited members (`inherited`, read-only, never sent to hosts), the console offers "Inherit from the application" and saves `null` for an inherited member, so the environment follows the application when it switches between block and log.
- The Postgres store failed with "bad connection" when saving an environment-scoped application setting: it ran the application-level statement and then a second one on the same transaction. It runs one.
- The control-plane API reads `outside_request` with the agents' grammar (characters up to U+0020 trimmed, not Go's wider Unicode spaces) and takes `null` to remove it.
- A primary Java agent start that fails now leaves no transformer and no thread of ours. The preload list is read and checked against the JAR before anything starts, so a missing list, an unreadable JAR or a listed class the JAR does not hold fails the start with nothing to undo; a class that cannot initialise, or any failure after the transformer was registered, removes the transformer and stops the control-file poller, the event writer (and its shutdown hook) and the direct-cloud client this start began. Before, a failure in `retransformAlreadyLoadedTargets`'s enumeration left the transformer registered. The launcher's `ohmyrasp-agent-start-failed` line now names the start's own error (for example the missing list) instead of `Unable to start OhMyRASP bootstrap agent`.
- The MyBatis statement scope (the hook on `BaseStatementHandler.prepare`, on every agent line) applies to MyBatis releases whose `prepare` takes only the `Connection`, such as the recorded 3.2.8; it matched only the `(Connection, Integer)` form that the recorded 3.4.6 and later have. The new run-time hook-miss check found it on the recorded 3.2.8.
- The Java 8, 11 and 17 agents start only with the copy of their classes that the injected calls reach. When the agent JAR was also on the application class path and the application used the line's classes there before an attach, the start either failed with `IllegalAccessError` or reported `installed` while the runtime the hooks use stayed unstarted, so nothing was detected. The start now fails cleanly first, naming the class and the loader that defined it.
- A shirudo upatch JAR keeps its baked settings, on every line, when a directory in its path ends in `!`. The settings were read through a `jar:` URL, which takes the first `!/` as the end of the archive name; the failure was swallowed and a locked JAR started unlocked, without its baked block mode. The file is now read from the JAR directly, and an upatch JAR whose settings are missing or cannot be read fails its start instead of running unlocked.
- A Java 8, 11 or 17 start that fails after its runtime has started (a transformer refused, a retransformation set-up error) removes the transformers it registered and stops the runtime: no thread is left and the hooks are inactive, as the launcher's `start-failed` says. Before, the runtime stayed published with its threads and earlier transformers.
- The backport shutdown hook waits for a start in progress, so it can no longer close the event spool before the start publishes a runtime configured for the writer thread; a start after the hook has run fails. A thread that stops the runtime's workers while interrupted still waits for them, and a failure while cleaning up no longer replaces the original error.
- On a Java 8, 11 or 17 thread that never enters a servlet request (a background worker), the same monitored attack repeated more than a second later is logged again; before, it was logged once for the life of the thread.
- The launcher's one-start lock is the `Instrumentation` interface's class object, which nothing else locks. The `Runtime` instance used before is a public monitor that Java 8 holds while it loads a native library.
- The Java 8, 11 and 17 agents retransform an already-loaded Janino `Cookable` on a dynamic attach, as the primary agent does.
- The Java 8, 11 and 17 agents log a monitored finding again in the next request on the same worker thread. Each hook remembered the last value it logged per thread for good, so the same attack repeated on a pooled thread in a later request, or after the log target changed, was not logged in monitor mode. The memory is now cleared when the outermost request enters and exits; an immediate repeat inside one request is still one event. Monitor mode writes more events than before.
- The Java 8, 11 and 17 agents stop their start when the agent JAR cannot be appended to the bootstrap search, or the line's hooks class does not resolve there afterwards. Before, the entry printed the error and registered transformers whose injected calls the bootstrap loader could not resolve, so instrumented JDK code could throw `NoClassDefFoundError`. The launcher now reports `ohmyrasp-agent-start-failed` and the JVM runs unprotected.
- The backport runtime starts all or nothing: the shutdown hook is registered before the control-poller and event-writer threads start, the runtime counts as started only once both have, and a failure stops what was started, so a failed start leaves no thread and can be retried. Before, a refused shutdown hook left both threads running unstarted, and a failure while the hook classes initialised left the runtime published although the start failed.
- A backport hook reached before the line has started does nothing and throws nothing. Before, it threw `ExceptionInInitializerError` into the caller and left the shared hook class unusable, so the line's later start failed with `NoClassDefFoundError`.
- The Java 8, 11 and 17 agents no longer load a class of their own for the first time inside a hooked call, where loading a class can re-enter the hook. The `rule-cases` probe found 38 to 43 agent classes per backport row loading during the cases' operations; each backport line now loads and initialises, before it registers a transformer, every class of its module and of `:shared` and the ASM classes they use, from a list the build writes into the JAR (`META-INF/ohmyrasp/preload/`). The probe now logs class loading and fails a case on a backport line when an agent class loads during it. On the primary line it reports them (133 to 135 classes per row, 17 of them lambda classes): a full preload there added 82 to 92 ms to the JVM start on JDK 25 and is not part of this change.
- The backport JARs have no invokedynamic call site left: the lambdas and method references of `shared/` code their hooks reach (servlet dispatch scopes, query-string fallback, HTTP submission tracking, MyBatis mapper analysis, the RocketMQ filter-server check) are anonymous classes, and the Java 11 and 17 modules compile string concatenation without `StringConcatFactory`. `check-dynamic-calls.py` now allows none, of any kind, on the backport lines.
- The launcher's one-start lock is the `Runtime` instance, which every definition of the launcher shares and no code can replace, instead of the system properties object, which `System.setProperties` can.
- The primary Java agent reads the text a hook asks of an object whose class is not public, through a public type of the object's hierarchy instead of its own class: the request URI and method of a Spark, YARN or DataEase request (Tomcat's package-private `ApplicationHttpRequest` overrides `getRequestURI`), the text of an expression object, the system id of an XML source and the target, method and arguments of a `java.beans.Statement` subclass. Before, the call failed silently and the event carried no request or the text was not inspected. The Java 8, 11 and 17 agents read the source of javac's own file objects (`com.sun.tools.javac.file.PathFileObject`, the unit for a file on disk) through `javax.tools.FileObject`; on Java 17 and later `setAccessible` on that class fails (`module jdk.compiler does not "exports com.sun.tools.javac.file"`), so such a source was never inspected.
- The per-line `deploy/shirudo/*/build.sh` scripts ran Gradle in `gradle:9.8.1-jdk25`, a copy of the pin that had moved on. They resolve the image from `java-agent/Dockerfile` like CI, as the caller's UID.
- The primary Java agent reads the source of a `javax.tools.JavaFileObject` that is not a public class. Compiling from a string with an anonymous `SimpleJavaFileObject` subclass, the usual way to do it, made the `getCharContent` lookup fail, so the source was never inspected and `java_compile_runtime` did not fire; the method is now resolved on a public type of the unit's hierarchy (`SimpleJavaFileObject`, `FileObject`). The backport agents already read such a unit.
- All four agent lines give Jetty 12 uploads the same filename inspection as Jetty 9.4 to 11. In Jetty 12 the servlet layer left jetty-server (`MultiPartFormInputStream` and `MultiParts` are gone there); its part classes are `ee10.servlet.ServletMultiPartFormData$ServletPart`, `ee9.nested` and `ee8.nested` `MultiPartFormInputStream$MultiPart` and `MultiPartInputStreamLegacyParser$MultiPart`, and `ee11` in 12.1. They were hooked only for denied archive uploads; they now go through the full upload check. The hook-target map records the ee8, ee9, ee10 and ee11 artifacts (12.0.41, and 12.1.15 for ee10 and ee11).
- The backport agents check the table name SkyWalking 9 writes into its log query. 9.x replaced `H2LogQueryDAO.queryLogs(String metricName, ...)` with `jdbc.common.dao.JDBCLogQueryDAO`, so the SQL-identifier hook matched nothing in storage-jdbc-hikaricp-plugin 9.7.0. It now covers `JDBCLogQueryDAO.buildSQL(..., String table)`, and the event names that source and the `table` parameter. The primary agent has no hook on this DAO; its request-field check for SQL identifiers is unchanged.
- All four agent lines hook janino's `Cookable` under its real name, `org.codehaus.commons.compiler.Cookable` (commons-compiler 2.7.8, 3.0.16 and 3.1.12 checked): `cook(String source)` and `cook(String fileName, String source)` hand the source to the compilation detector. The old name, `org.codehaus.janino.Cookable`, exists only in janino 2.5 and earlier.
- All four agent lines inspect the source a janino compilation is given as text once, and never take a file name for source. The hooks on `SimpleCompiler`, `ClassBodyEvaluator`, `ScriptEvaluator` and `ExpressionEvaluator` took the first `String` of `cook(String fileName, Reader)` for the source, but that `String` is the file name, so a `Reader` was never read and a file name that looked like code could be reported. They are gone. The one janino hook is now commons-compiler's `Cookable.cook(String fileName, String source)` at its source argument; `cook(String source)` calls it, so it is no longer hooked as well and one compilation gives one report (before, `cook(String)` reported the source twice: the primary agent logged two lines in monitor mode and blocked on the first in block mode; the backport agents' monitor mode already dropped an identical second line). Source that exists only as a `Reader` or `InputStream` is still not inspected, which [docs/detection.md](docs/detection.md#runtime-java-compilation) lists with the other limits. Janino 2.7.8, 3.0.16 and 3.1.12 checked.
- All four agent lines trace the SQL that PageHelper 4.2.x dialects compose: `getPageSql(String, Page, RowBounds, CacheKey)` is hooked next to the 5.x `(String, Page, CacheKey)` and `(String, RowBounds, CacheKey)` forms. With pagehelper 4.2.1 no dialect method matched (hooked methods 0 to 12 per agent family).
- The primary Java agent hooks Struts 7's `org.apache.struts2.ognl.OgnlUtil` (`getValue` and `setValue` with an expression string), as it does the `com.opensymphony.xwork2.ognl` one of Struts 2.3 to 6.x. With struts2-core 7.0.3 the hook matched nothing, and OGNL expressions that Struts evaluates were no longer handed to the expression detector there (hooked methods 1 to 4).
- The backport agents no longer name `org/apache/commons/jexl2/ScriptImpl`. JEXL 2.0, 2.0.1, 2.1 and 2.1.1 have no such class (scripts run in `ExpressionImpl`, which stays hooked); `ScriptImpl` exists only in JEXL 1.x, in the `org/apache/commons/jexl` package.
- All four agent lines no longer name `com/alibaba/com/caucho/hessian/io/UnsafeDeserializer`. Hessian Lite has no such class in any release (2.6.2 and 3.2.2 to 3.2.13 checked), so the name matched nothing; Caucho Hessian's own `UnsafeDeserializer` is still hooked.
- The primary Java agent no longer names `org/snakeyaml/engine/v2/constructor/*` as a hook target. SnakeYAML Engine (2.0, 2.10 and 3.2 checked) never resolves a tag to a Java class, so the `getClassForName` hook it wanted matched nothing; the snakeyaml 1.x `Constructor.getClassForName` hook is unchanged.
- The daemon no longer reinitialises a control file whose `mode` an operator edited to a spelling the agents accept (`record`, `observe`, `log`, `disabled`, `none`, `blocking`, `protect`, or another letter case). It keeps the document and writes the canonical `off`, `monitor` or `block` the next time it writes the file. Both agent engines accept the same set of spellings.
- The daemon refuses to write a control document larger than the agents read (a large cloud policy used to be written, and the agents then ignored the whole file, mode changes included). It keeps the previous document, logs an error that names the size and the limit, and reports the refusal in `/api/stats`, `/metrics` and the local console. The limit is one value in `java-agent/contracts/agent-daemon/control/limits.properties`, which the daemon and both agent engines test their own constant against. The size is measured on the file as found at start-up: a hand-edited file padded past the limit, which the agents were ignoring, is written again when its document fits (the log and `control_status.oversized_file_replaced` say the agents apply it from then on), and when it does not fit the refusal says the agents are not applying the daemon's in-memory state (`control_status.write_refused.agents_apply_state` is false, and stays false for any later refused change while the file on disk is still over the limit). A refused cloud policy is logged once per assignment (its id and version, else a hash of its text) and no longer once per document size; the policy version the daemon reports upstream is the one last written successfully to the control file, never the assignment (so a refused policy, or one whose download failed, is not reported as active); and the refusal indicator clears when the cloud's policy becomes the installed one again.
- The daemon no longer reads the backport agents' start line as a detection: it is not counted in the attack log and not uploaded (it was shown as a low-severity "agent event"). It fills the `agent` entry of `/api/stats` instead. A line with a `kind` the daemon does not know is not a detection either; it is counted under `ignored_kinds`, as is a line whose `kind` is present but not a string (under `(non-string)`), which is never read as a detection from its other members. At most 32 distinct kinds are kept (a label is cut to 64 characters, and later kinds are counted under `(other)`), so a spool producer cannot grow the map.
- `/api/stats` reads the control state and the status of its last write in one snapshot.
- The daemon reads the backport agents' numeric epoch-millisecond `timestamp`, so an uploaded detection carries the time it happened and not the time the daemon read it.

### Added
- Every Java agent line reports, at run time, a hook that was meant for a loaded library class and did not apply: a release that renamed a hooked method or changed its descriptor no longer passes silently on a version the `hook-targets` probe never saw. One diagnostic line per hook unit and class per JVM (`"kind":"diagnostic"` with `"diagnostic":"hook_miss"` on the primary agent, `"event":"ohmyrasp-hook-miss"` on the Java 8, 11 and 17 agents) names the hook module or transformer, the class, the methods it looks for, the methods of the same names the class has, and the JAR the class came from with its `Implementation-Version`; at most 32 lines, then one suppressed line. The expectations are generated from the probe's recorded maps into every agent JAR; a reviewed list, `probes/hook-targets/hook-miss.toml`, explains the gaps between recorded versions, and the probe now runs the real transformers with the report on over every recorded library JAR and fails on a gap it does not explain. The daemon shows the lines in `/api/stats` (`hook_misses`) and its log and never uploads them as attacks. See [docs/agent.md](docs/agent.md#hooks-that-did-not-apply).
- `outside_request` (`block` or `log`): one setting, read by every agent line, that turns blocking of context-dependent findings outside an HTTP request into "log only". It does not turn off findings whose argument is the exploit itself. A connection to the cloud metadata address made by a cloud provider's own credential or metadata client (AWS, Google, Azure, Alibaba, Tencent and Huawei SDK classes on the stack) is logged outside a request whatever it says, and so are three request-defined primary rules (`ssrf_protocol`, `ssrf_obfuscate`, `ssrf_userinput`). Two parties set it and blocking needs both to allow it: the host, as the control document's top-level member, written by the daemon's console (`POST /api/control`, `null` clears it, and a switch on the host dashboard that shows what the agents apply and who decides it); and the cloud, as the `outside_request` member of the per-application or per-environment `protection.hardening` setting on the console's Protection page, which reaches the agents inside the policy (`config.hardening.outside_request`) and leaves with it. An environment without the member inherits the application's. A standalone agent reads it like `mode` (`-Dohmyrasp.outside_request`, `OHMYRASP_OUTSIDE_REQUEST`, baked properties, and on Java 21 and 25 the agent argument); the universal Shirudo JAR bakes it (`-PshirudoOutsideRequest`, `build.sh --outside-request`). Default `block`. [Configuration keys](docs/agent.md#configuration-keys)
- A rule case can carry a control document (`control = { outside_request = "log" }`); the `rule-cases` probe then runs the agent daemon-managed with that file.
- Every agent line now sees an HTTP request body as the application reads it. It records what the application's own read calls return from the servlet input stream (any class whose direct superclass is `javax`/`jakarta.servlet.ServletInputStream`: Tomcat, Jetty, Undertow, Spring's caching wrapper) and from Tomcat's reader, up to the first 8192 bytes or characters of a request, and never reads the body itself. JSON keys and string leaves, form values and other text join the request input the rules consult: a sink rule matches them as it matches parameter values, and the request rules run again on each new body state, in the read that completes the body or before the next hook's decision. Before, no line saw a body, so an attack that blocks as a query parameter (`127.0.0.1; id` reaching a shell, `/etc/hosts` reaching a file read, a SpEL path in a JSON Patch document) passed in a JSON body. The `rule-cases` probe records the change: on the primary agent 19 cases now block, among them the 13 `-in-json-body` cases, and `request_json_patch_expression`, `request_message_selector_expression` and `request_xml_polymorphic_gadget` are no longer "defined, not wired"; on the Java 8, 11 and 17 agents the cases of the rules they have block the same way. An event on a request with a body shows the one input field its rule matched, with that field's value, and no other body text (see Security above), and the agent overwrites what it recorded when the request ends. A read that throws releases the recording, a read of another stream than the one whose read first returned data records nothing, a block on the body is thrown again by every later read of that stream, and every request-rule finding on the body is reported, not only the chain's first. Limits (unread bodies, the cap, binary and multipart bodies, reads on another thread, non-servlet stacks): [docs/detection.md](docs/detection.md#request-bodies).

  every JVM on a host, Java 8 to 25. It is the default a shirudo operator installs; the per-line packages stay

  `verify-shirudo-upatch.sh` checks the launcher entry, all four lines and the baked properties. `ohmyrasp.jar`
  and `ohmyrasp-agent-all.jar` are release assets, and the Beefile bundle carries the new package.
- `deploy/shirudo/gen-readmes.py`: auto-generates `deploy/shirudo/README.md`
  and per-track `ohmyrasp-{java8,java11,java17,jdk25}/README.md` with

  `deploy/shirudo/verify-shirudo-upatch.sh` enforces `--check`.
- `docs/images/architecture.svg`: architectural overview diagram in root READMEs.

### Changed
- The primary Java agent (JDK 21 and 25) no longer loads a class of its own for the first time inside a hooked call. Before, the `rule-cases` probe saw 133 to 136 agent classes load during the cases' operations on each primary row. Like the backports, it now loads and initialises, before it registers its transformer and on `premain` and `agentmain` alike, every class of its module, the `:shared` classes it reaches and the ASM classes they use, from a list the build writes into the JAR (`META-INF/ohmyrasp/preload/agent-jdk25.txt`; the universal and the Shirudo JARs carry it too, and `verifyPreloadLists` fails a JAR that can start a line without that line's list). The probe now fails a primary case when an agent class loads during it: 0 of 221 cases on the `jdk21` and `jdk25` rows, with the line JAR and with the universal JAR. The owner accepted the start cost on 2026-11-27 (time on application threads is the constraint, start time is not): JVM start to `main` with `-javaagent` rose from 355 to 443 ms on JDK 21 and from 356 to 489 ms on JDK 25 (median of 30 runs on a shared machine; preload and warm-up together, the preload alone 419 and 452 ms).
- The primary agent runs one pass of its request, SQL and deserialization hooks on harmless in-memory input at start (`Warmup`), before the transformer is registered, so linking their lambdas and loading the JDK classes they first use happens at start. It reads no file, opens no socket, starts no process and writes no event (`WarmupTest` checks the event log stays empty with blocking on). The first call of the request hook, timed in-process, fell from 23.0 ms to 2.7 ms on JDK 21 and from 30.9 ms to 2.8 ms on JDK 25 (13.2 and 16.5 ms with the preload alone; median of 20 runs). The hidden classes of lambdas cannot be on a list: the probe reports 24 of them, from 15 source classes, created during the cases' operations (32 from 17 before the warm-up), and does not fail on them; the primary's JAR holds 107 lambda and method-reference call sites in all.
- The primary agent compiles with `-XDstringConcat=inline`, as the backports do: its JAR lost 104 string-concatenation call sites (364 invokedynamic sites in 91 classes became 260 in 77), so a concatenation in a hook is no longer linked on its first use inside a JDK call.
- On an attach to a running JVM the primary agent starts on the JVM's `Attach Listener` thread, as any agent does, and the application's own threads are paused only by the retransformation of the classes already loaded. Measured with a thread that timestamps every millisecond, the largest gap around an attach was 9.1 ms on JDK 21 and 9.7 ms on JDK 25 with this change (7.0 and 6.3 ms before it; 3.8 and 3.9 ms with no attach; median of 20 runs). `agentmain` took 358 and 404 ms (275 and 270 ms before).
- Every agent line decides with one definition of "inside a request" and one classification of findings outside one ([Outside an HTTP request](docs/detection.md#outside-an-http-request)). A finding is inside a request when the thread serves one, when the hook carries the request that started the operation onto the thread doing it (an HTTP client exchange, a directory walk, a CXF attachment), or when the hook holds the request (Spark, YARN, DataEase); the Java 8, 11 and 17 agents decided by the thread alone, so such findings on a worker logged under `outside_request=log` while the primary blocked them. Outside a request: a finding whose argument is the exploit itself (a listed gadget type, a remote JNDI name, the Base64 tail-underflow shape, exploit shell syntax, an expression language reaching the process API, the Spring, RocketMQ, CXF, OpenWire, Hessian, Fastjson and XML-RPC checks) blocks in block mode whatever `outside_request` says; a cloud provider's credential client reading the metadata address and the primary's `ssrf_protocol`, `ssrf_obfuscate` and `ssrf_userinput` log whatever it says; the rest, a remote class, a remote Spring configuration, a remote DTD or entity and the metadata address included, blocks by default. In block mode the primary agent (Java 21 and 25) now blocks those last findings outside a request, as the backport agents did; before, it recorded them as `log`, or for sensitive host reads, script writes, Java compilation, XMLDecoder statements and MySQL JDBC URLs did not decide them at all.
- A connection to the cloud metadata address outside an HTTP request, made by a cloud provider's own credential or metadata client, is logged and no longer blocked on every line: a frame of one of the SDK classes `OutsideRequest` lists (each checked in a released JAR from Maven Central) is on the thread's stack and there is no request evidence. The same connection from application code, a class loaded from a remote URL, a remote DTD or entity and a remote Spring configuration still block outside a request in block mode, as the Java 8, 11 and 17 agents blocked them before; the primary agent now does too. The class is recognised by name: an application that ships a class with an SDK's name can make its own metadata access log instead of block outside a request, never inside one. [Outside an HTTP request](docs/detection.md#outside-an-http-request)
- A launch whose arguments are an exploit's (a reverse shell, `cat /etc/passwd`) is no longer let through under `outside_request=log` because a Groovy or JavaScript script, Solr's configured listener, a database routine or an XXL-JOB shell job started it: the intrinsic argument check runs before such a context-dependent stack finding is used, and an expression language below a script engine on the stack decides as expression evaluation. Inside a request the event can now name the intrinsic rule (`command_common`, `command_arguments`) instead of the stack's.
- On the primary agent an HTTP client exchange with no captured origin, run on a thread that serves a request, is inside that request, as on the backports. Before, its metadata or internal destination was decided as outside a request.
- The primary agent's Java compilation rule (`java_compile_runtime`) decides inside a request with the backports' text rule too, which also matches a single-quoted reflective `getMethod('start')` (text a comment or a string literal holds), and the MySQL rule reports a URL the request did not supply with confidence 92 (95 when the request supplied it).
- The primary agent's RocketMQ rule (`command_config_injection`) requires shell operators in the program the filter-server manager launches, as the backports' does: the broker's own filter-server start has none, and was reported.
- The MySQL rule (`jdbc_mysql_deserialization`) is one rule on every line, matching the two chains that read server bytes at connect time: `autoDeserialize` with `ServerStatusDiffInterceptor` as an interceptor, or with `detectCustomCollations`. It reads the URL with Connector/J's grammar (checked against 8.0.33 and 5.1.49 as oracles): options are parsed keys and values, the last repeated key wins, a host's own `address=(...)` or `(...)` options apply to it, and the interceptor is an entry of the list, not a substring. A pool that sets `autoDeserialize` beside an interceptor of its own, or a URL that only names these words in another option's value, no longer fails to connect in block mode; `jdbc:mysql+srv:` and percent-encoded option values are now read, and a query whose `=` and `&` are percent-encoded, which neither driver line reads as options, is not reported. The backports now cover `jdbc:mariadb:` too.
- Every agent line leaves Tomcat's own WAR unpack and JSP compile alone by watching the operation itself, instead of matching class names on the stack under `catalina.base`. `ExpandWar.expand` and Jasper's `Compiler.compile(boolean, boolean)` are hooked (recorded on Tomcat 7.0 to 11.0 and Jasper 9.0, 10.1 and 11.0) and record, from the container's own objects, the docBase (`host.getAppBaseFile()` and the pathname) or the context's output directory they write; only writes under that directory, on that thread, during that call are exempt, and only when the class, its caller and the `Host` or compilation context come from a loader that is not a web application's. A Host whose `appBase` lies outside `catalina.base` (for example `/srv/webapps`) unpacks its WARs in block mode again (checked on real Tomcat 9.0, 10.1 and 11.0 with the primary on JDK 21 and the Java 17 line: zero events, and a `.jsp` the application writes into the same directory still blocked); a script written elsewhere under `catalina.base` during an unpack, and classes named like Tomcat's in an application's loader, get no exemption. The `WEB-INF` exemption reads the path with `..` resolved. [Host writes](docs/detection.md#host-writes-and-archive-entries)
- The backports' script-write rule leaves Tomcat's WAR unpacking and JSP compilation alone in the rule itself, not only in the `FileOutputStream` hook, so every line that uses the rule skips them.
- The Java 8 general JAR (`ohmyrasp-agent-java8.jar`) no longer names `Boot-Class-Path: ohmyrasp-agent-java8.jar`. A renamed copy beside another build of that name used to put the sibling's classes on the bootstrap loader before the launcher chose a line; the Java 8 line now appends the JAR it was started from, as every other line and JAR already did.

Each line keeps its entry class, transformers and block exception, a `Java<N>RaspLine` that names its rule-id prefix, properties, environment variables, threads and log prefix, and a `Java<N>RaspHooks` whose public methods (same names and descriptors) each call the shared method. No behaviour change is intended: rule ids, messages, property and environment names, thread names and the event and control formats are unchanged, and the contract examples compare equal. The entry class now starts the line explicitly before it registers any transformer, and the shared runtime refuses to run before that; the start also loads the shared hook classes and `RaspRuntime.Mode`, which a hook used to load the first time it ran when no mode was configured. The backport JARs have no invokedynamic call site left in the decisions (`check-dynamic-calls.py`: 10 lambda sites per backport line, from 12).

### Fixed
- **Java agent (all 4 tracks):** the baked `META-INF/ohmyrasp-shirudo.properties`
  is read only from the agent's own JAR. Before, a same-named file in a JAR on
  the application class path was read in its place and could switch a locked
  `mode=block` agent to `off`. A baked file that is malformed part-way keeps the
  keys read before the malformed line.
- **Java agent (all 4 tracks):** an unrecognised `mode` or `standalone` value in
  one source is skipped and the next source applies, so a mistyped value no
  longer hides a valid `block` and leaves the agent not blocking.
- **Java agent (`java8`/`java11`/`java17`):** the three lines share one runtime.
  On `java11` and `java17`, `lock_config=true` now ignores system properties and
  environment for `standalone`, `mode` and `control` even when a baked key is
  missing, and standalone with no mode configured resolves to `block`. On
  `java8`, the event writer thread starts when the agent loads (only when the
  log target is a file), not inside a hook.
- **Java agent (all 4 tracks):** a `lock_config=true` profile without a baked
  `control` path no longer polls `/tmp/ohmyrasp-control.json`.
- **Java agent (all 4 tracks):** the control file is read on every poll and
  applied when its content changes, not its modification time, so a document
  read half-written is applied once complete. When the file is removed, the
  mode (and on `agent-jdk25` the per-algorithm switches, the revision and a
  policy the file installed) return to their start-up values together, so an
  `ignore` rule from a removed control file stops suppressing detections; a
  policy installed by the direct-cloud client stays. An unreadable file keeps
  the last good state.
- **Java agent (`agent-jdk25`):** a control file rewritten without `policy`
  (how the daemon withdraws one) drops the policy the file installed, so its
  `ignore` rules stop suppressing detections. Policy text that does not parse is
  no longer recorded as applied, so it cannot later reinstall the file's
  unchanged policy over a direct-cloud one.
- **Java agent (all 4 tracks):** only well-formed control-file content changes
  anything: at most 1 MiB (the reader stops one byte past that bound), strict
  UTF-8, and exactly one JSON object, with `mode` read from its top level. A
  truncated document, a nested `mode`, a number such as `01`, non-ASCII escape
  digits or malformed UTF-8 no longer switch detection. Nothing thrown while the
  file is read leaves the poll step, an `Error` from a file system provider
  included, so the first read at agent start cannot abort the application's
  start-up, and no error stops the poller.
- **Java agent (`java8`/`java11`/`java17`):** standalone mode never polls a
  control file, as on `agent-jdk25`; before, an explicitly set control path was
  polled in standalone mode.
- **Java agent (all 4 tracks):** an invalid control path, poll interval or
  `ohmyrasp.log.sync` value no longer hides a valid lower-priority value; on the
  backports the same holds for `ohmyrasp.java{8,11,17}.block`, and on
  `agent-jdk25` for `ohmyrasp.latency_sample` and `ohmyrasp.log.queue`.
- **Java agent (all 4 tracks):** the shutdown hook waits up to 2 seconds for the
  event writer, then writes what is still queued waiting up to 1 second for the
  write lock, and an event submitted after that is written inline. These are
  bounded waits; events accepted while the JVM is shutting down may be lost. On
  the backports a queued event is written to the log target it was accepted for.
- **Java agent (all 4 tracks):** a detection decided as a block is blocked even
  when recording its event fails (for example a replaced `System.out` that
  throws while events go to the console); before, the operation went ahead.
- **Java agent (`agent-jdk25`):** the event logger and the hooks' static state
  are initialised before the first transformer is added, so no hook starts the
  event writer or registers its shutdown hook, and the logger's standalone
  defaults follow the `standalone` value the runtime resolved.
- **Java agent (all 4 tracks):** the agent's own event and control-file I/O is
  no longer reported or blocked by its file hooks, so a spool path such as
  `webapps/ROOT/events.jsp` no longer aborts or hangs the JVM in block mode,
  and it no longer uses up a pending archive entry the application's next
  write is checked against.
