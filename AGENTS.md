# Agent and contributor rules

Build, test and PR workflow live in [CONTRIBUTING.md](CONTRIBUTING.md). This file holds the rules that are easy to break without noticing.

## After a change

```bash
python3 scripts/gates.py changed          # which checks this change triggers, and why
python3 scripts/gates.py run --changed    # run them
```

`scripts/gates.py` holds the table of checks per path. Add `--slow` before a pull request that touches the Java agents: it runs every probe on every agent line. Rules for one component live beside it: [java-agent/AGENTS.md](java-agent/AGENTS.md).

## Java source files

Keep each Java file at or below 5,000 physical lines. Split production code and tests by responsibility. Run `python3 scripts/check-java-size.py` to check the working tree.

## Documentation

**One home per fact.** A value that changes as releases ship or code evolves lives in exactly one place: its source file, or a generated document or region. Other docs describe the kind of thing and link to that home. A copy in prose goes stale silently, and the next release does not update it.

| Fact | Its home | Write in docs instead |
|---|---|---|
| Current release version | git tags and [GitHub Releases](https://github.com/xuing/oh-my-rasp/releases) | A link to Releases, or `<version>` and `VERSION=<version>` in commands |
| Release asset list | `**GitHub Release assets**` in [docs/runbooks/release.md](docs/runbooks/release.md), matched to `EXPECTED_ASSETS` in `.github/workflows/ohmyrasp-release.yml` | The kinds of assets, and a link to that list. Never a count. |
| Toolchain and image versions | `api/go.mod`, `daemon/rust-toolchain.toml`, `console/package.json`, each `Dockerfile` `FROM`, each compose `image:` | "pinned in `<file>`". Commands resolve the image the way CI does: `awk '$1 == "FROM" && $2 ~ /^gradle:/ { print $2; exit }' java-agent/Dockerfile` |
| Hook, detector, signature and scenario counts | [java-agent/docs/DETECTION-COVERAGE.md](java-agent/docs/DETECTION-COVERAGE.md), generated by `java-agent/scripts/gen-detection-coverage.py` | A link. The README "By the numbers" table is a generated region from the same script. |
| False-positive corpus results | [java-agent/docs/FALSE-POSITIVE-REPORT.md](java-agent/docs/FALSE-POSITIVE-REPORT.md), generated by `java-agent/scripts/run-fp-report.sh` | A link |
| Vulhub roots and CVE counts | Source Audit in [docs/development/vulhub-coverage.md](docs/development/vulhub-coverage.md), checked by `java-agent/scripts/check-vulhub-java-coverage.py` | A link |

Fixed facts can be written out: CVE IDs, versions of vulnerable third-party targets, supported runtime lines (JDK 8/11/17/21/25, Tomcat 9/10/11), dates, and the steps of a specific past migration. `CHANGELOG.md` and `docs/internal/` are history by design.

**Generated docs.** Never hand-edit a file that starts with a "Generated by" header, or text between `<!-- BEGIN GENERATED <slug> ... -->` and `<!-- END GENERATED <slug> -->`. Change the generator's inputs, rerun it, and commit what it writes:

```bash
python3 java-agent/scripts/gen-detection-coverage.py   # DETECTION-COVERAGE.md + README metrics regions
python3 deploy/shirudo/gen-readmes.py                  # deploy/shirudo READMEs
```

**Check before you push.** `python3 scripts/check-docs.py` runs in CI (`.github/workflows/docs.yml`). It fails when:

- a generated doc is stale, or its generator fails;
- a released tag or a pinned version is copied into a doc;
- a hand-written count appears outside a generated region;
- the release asset list drifts from the workflow;
- a relative link in a hand-written doc does not resolve to a tracked file, or its `#anchor` matches no `## heading` or `<a id>` of the target. Links inside generated files and regions are left to their generator;
- a line of an evidence ledger ([vulhub-coverage.md](docs/development/vulhub-coverage.md), [algorithm-coverage.md](docs/development/algorithm-coverage.md)) that names an acceptance script names one that is not tracked, has a backticked rule id from `java-agent/rules/*.json` that is not a whole word in every script the line names, or has a backticked word shaped like a rule id that the catalog lacks. The scenario labels in the parenthesis that opens a Covered Targets row, up to its first `;`, are not checked against the script;
- a script under `java-agent/acceptance/vulhub/` is not named on a `- [x]` row of the Vulhub ledger's Covered Targets.

When it flags something, link to the fact's home. Do not reword the text just to get past the pattern.

**Keep translations paired.** A change to `README.md` needs the same change in `README.zh-CN.md`.
