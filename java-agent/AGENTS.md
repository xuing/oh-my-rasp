# Java agent rules

What lives where under `java-agent/`, which command checks a change, and the rules that are easy to break here. Build and packaging details are in [README.md](README.md); the full contributor workflow is in [../CONTRIBUTING.md](../CONTRIBUTING.md#java-agent).

## Layout

| Path | Holds |
|---|---|
| `agent-jdk25/` | The primary agent, for JDK 21 and 25. |
| `agent-java8/`, `agent-java11/`, `agent-java17/` | The backport lines. Three source trees, each written for its own JDK, holding what is really per line: the entry class, the transformers, the line descriptor `Java<N>RaspLine`, the block exception, and `Java<N>RaspHooks`, the class the transformers call, whose methods are one-line calls into the shared decisions. |
| `shared/` | The `:shared` module, compiled once with `--release 8`: the classes every line carries, among them the backport decisions and runtime (`io.ohmyrasp.agent.backport`: `BackportHooks`, `RaspRuntime`, `BackportLine`), the launcher (`io.ohmyrasp.agent.launch.AgentLauncher`) and, generated by `src/entryGenerator` as class-file version 49 so that Java 6 and 7 can load them, one entry class per kind of agent JAR (`UniversalEntry`, `PrimaryEntry`, `Java17Entry`, `Java11Entry`, `Java8Entry`). |
| `agent-all/` | The universal JARs: every line, one copy of `shared/` and of shaded ASM. Nothing is compiled here. |
| `backport-tests/` | The unit tests of the three backport lines, written once. |
| `contracts/` | Example event lines and control documents shared with the daemon; the agent and daemon tests both read them. |
| `probes/` | Packaged-agent probes, one directory each, and the registry that runs them. |
| `acceptance/` | End-to-end suites: `runtime/` per JDK, `vulhub/<component>/` per Vulhub target. |
| `rules/` | Rule descriptions. The detection coverage doc is generated from them. |
| `rules/cases/` | Rule cases: per rule id, inputs and what each engine does with them today, run on every line by the `rule-cases` probe. |
| `scripts/` | Generators and checkers. |

## After a change

```bash
python3 scripts/gates.py run --changed                 # from the repo root: the checks this change triggers
java-agent/scripts/check-agent.sh --line java17 file-read   # one line: unit tests, then one probe on that line's JDK
java-agent/scripts/check-agent.sh --artifact all --line java17 file-read   # the same probe against the universal JAR
java-agent/scripts/check-agent.sh --help               # lines and probes
```

`check-agent.sh` takes several lines at once (`--line java8,java11,java17`) and `all` in place of a probe name.

## Rules

**A backport change reaches all three lines.** The decisions of `agent-java8`, `agent-java11` and `agent-java17`, and their runtime, live once, in `shared/src/main/java/io/ohmyrasp/agent/backport/`: change a rule there and it changes on every line. What differs between the lines comes from the line descriptor (`BackportLine`, one `Java<N>RaspLine` per line); add a per-line name there, not a branch on the line. The transformers, entry classes and `Java<N>RaspHooks` delegates stay three copies that may differ in syntax, never in what they do: make the same change in each line in the same commit. Put a backport test in `backport-tests/`, where one test runs on all three. A test that only one line can run stays in that line's `src/test` and says why in its first line. `scripts/check-backport-drift.py` compares the three trees after replacing the version token and fails on a difference that [`scripts/backport-drift.java11.diff`](scripts/backport-drift.java11.diff) and [`scripts/backport-drift.java17.diff`](scripts/backport-drift.java17.diff) do not record. Record a difference you mean (newer syntax, a per-release constant) with `--update`, and say why in the commit.

**Backport lines have no invokedynamic call site.** Their hooks run inside JDK bootstrap classes, where the first use of a lambda, a method reference, a record's generated `toString`/`equals`/`hashCode`, a pattern `switch` or a `StringConcatFactory` concatenation links at run time and can re-enter the hooked call. Write an anonymous or static nested class there, also in `shared/` code a backport hook reaches; the three backport modules compile their own sources with `-XDstringConcat=inline`, and so does `agent-jdk25`, whose lambdas, method references and records stay (the baseline records them). `var`, text blocks, `switch` expressions over strings or enums and `instanceof` patterns compile without such call sites and are fine. `scripts/check-dynamic-calls.py --check` reads the built JARs, shaded classes included, and fails on any call site, of any kind, on `java8`, `java11` or `java17`: the rule is none, in the script itself, and `--update` refuses to record one for them ([`scripts/dynamic-calls.baseline.json`](scripts/dynamic-calls.baseline.json) records only the primary line). `check-agent.sh` runs it for backport lines.

**A hook loads no class of ours for the first time, on any line.** Each agent module writes, at build time, the list of its classes and of the `:shared` classes it reaches (and the ASM classes they use) into its JAR, `META-INF/ohmyrasp/preload/<module>.txt` ([`gradle/preload-index.gradle.kts`](gradle/preload-index.gradle.kts)): a backport lists all of `:shared`, the primary only what its own classes name. The line loads and initialises every one of them before it registers a transformer (`io.ohmyrasp.agent.util.Preload`), on `premain` and on `agentmain`. A new class is on the list without anything to do, and a JAR that can start a line without that line's list fails `verifyPreloadLists`. Time spent at start is not a constraint; time on an application thread is. The `rule-cases` probe runs each case with class-load logging and fails a case, on every line, when a class under `io.ohmyrasp.agent.` loads during its operation. The hidden class of a lambda or method reference cannot be on a list (it does not exist until its call site first runs): a backport case fails on one, and on the primary they are counted per source class and reported (`ENFORCED_HIDDEN` in the probe). The primary also runs one pass of the entries its modules inject on the request path (servlet admission, request-body reads, the JDBC entry, the deserialization filter) on harmless input before its transformer is registered (`io.ohmyrasp.agent.hook.Warmup`), on a thread of its own and with a logger that writes nothing: a hook added there must read no file, open no socket and start no process, and `WarmupTest` must still find the event log empty and `stderr` silent. A static initialiser of a preloaded class must not build JDK objects whose class reads a setting once (`InetAddress`, a security provider, `java.util.logging`, a default `Locale` or `TimeZone`): keep such constants as plain values, as `NetworkHost` keeps its addresses as bytes.

**Every primary hook entry checks `HookActivation` first.** Removing a transformer does not remove the calls it injected, so each public entry of `OhMyRaspHooks` and `DeserializationGuard` begins with `if (HookActivation.inactive()) return ...;`, returning what the uninstrumented code would have had; the flag turns on when a start commits and off first in its undo. `HookActivationTest` reads the bytecode and fails on an entry without it.

**The event and control-file formats are pinned by examples.** A change to what an agent writes to the event spool, or to how it reads the control file, fails a test against [`contracts/agent-daemon/`](contracts/agent-daemon/README.md). Regenerate the examples there as its README says, read the diff, and run the daemon tests too: the daemon parses the same files.

**`shared/` stays Java 8 source.** `:shared` compiles it once with `--release 8`, and every line's JAR carries that bytecode.

**The launcher loads nothing of ours before it chooses a line and never lets a start failure stop the JVM.** `AgentLauncher` uses only `java.*`, looks for line entry classes in the entry class's own JAR file, and catches every `Throwable` from the line it starts; [docs/agent.md](../docs/agent.md#which-jar-to-attach) says what it prints. Keep it plain Java 8 without lambdas: it runs on every Java version a JAR can be attached to. Each JAR packs only its own entry class, and the root `verifyLauncherEntries` task fails when a JAR holds another one or names another in its manifest. The launcher's range table has a Python twin in `probes/common/agent_track.py`, which the `launcher` probe checks against the real launcher.

**Probes are registered by directory.** A new probe is a directory under `probes/` with a `check.py`, plus a `probe.toml` when it needs staged fixtures or applies to some lines only (give the reason). Do not name a probe in a workflow or script: both call `probes/run.py`.

**Acceptance scripts are found by path.** A new one goes in `acceptance/vulhub/<component>/<scenario>-<jdk>.sh` or `acceptance/runtime/`. A script anywhere else is not counted by the coverage tooling.

**Acceptance scripts build through the helper.** A Vulhub script sources `acceptance/lib/agent-build.sh`, builds with `ohmyrasp_build <gradle tasks>` and reads its agent JAR path through `ohmyrasp_agent_jar`; never write `docker run ... gradle` (with or without a path), a host `gradle` or `./gradlew` build, or a `gradle:` tag in a script (`"$(ohmyrasp_gradle_image)"` is the pinned image when a script needs a JDK container). The helper runs Gradle in the image pinned by `Dockerfile`, as your uid, with `GRADLE_USER_HOME` in `${OHMYRASP_GRADLE_HOME:-~/.cache/ohmyrasp-gradle-home}` (a relative `OHMYRASP_GRADLE_HOME` is taken from the current directory). `OHMYRASP_AGENT_JAR=/abs/path.jar` runs a script against a prebuilt JAR (the script mounts that JAR and builds nothing), and `OHMYRASP_SKIP_AGENT_BUILD=1` skips the build when you ran Gradle yourself. `scripts/check-acceptance-build.py` enforces this. The `runtime/` suites build the agent inside their Docker images (`Dockerfile*`) and do not use the helper. A script that needs a file from a Vulhub checkout finds it under `${OHMYRASP_VULHUB_ROOT:?set OHMYRASP_VULHUB_ROOT to a Vulhub checkout}`; its own per-script variable, where it has one, still overrides the full path. No script names a path on one person's machine, and `scripts/check-acceptance-build.py` fails on one.

**A hook aimed at a library is recorded against real versions.** A hook that matches a third-party class and method stops applying, silently, when a release renames them. Adding or changing one means adding the library and its versions to [`probes/hook-targets/libraries.toml`](probes/hook-targets/libraries.toml) (the oldest still common, one where the API changed, the newest, and one line saying why), running `java-agent/scripts/check-agent.sh --line jdk25 hook-targets --update` and, for a backport hook, `--line java8,java11,java17 hook-targets --update`, and reviewing the diff of `probes/hook-targets/recorded/` and then `python3 java-agent/scripts/gen-hook-targets.py`. A library version with no hooked method needs a `none` entry with its reason in `libraries.toml` (a reason that starts with FINDING marks a hook to fix, not to accept); a hook family that hooks no library (it targets the JDK, or an application class) is listed in `probes/hook-targets/allowlist.toml`, which the probe keeps minimal. [`docs/HOOK-TARGETS.md`](docs/HOOK-TARGETS.md) is generated from the recorded maps. The same probe has the row's own JVM define and verify every class a hook rewrites in those JARs, and a set of synthetic read methods (`probes/hook-targets/HookVerify.java`): a rewrite the JVM rejects fails it, on every row.

**A primary-agent rule lives in its family's detector class.** Hooks in `agent-jdk25` call the class in `agent-jdk25/src/main/java/io/ohmyrasp/agent/detect/` that owns the decision, and its tests are in `<Detector>Test` beside the other detector tests; [docs/detection.md](../docs/detection.md#primary-agent-detector-layout) maps each kind of evidence to its class. `DetectorEngine` holds only the HTTP request chain, whose first-match order `DetectorEngineDispatchTest` pins. Put a helper that a second family needs in a shared utility of the package (`DetectorStrings`, `FilePaths`, `RequestDecoding`, `RequestValues`, `RequestJson`), not in one of the families. To check one family, run `java-agent/scripts/check-agent.sh --tests '*FileAccessDetectorTest'`, with that family's test class in place of `FileAccessDetectorTest`.

**A new rule id needs a description.** Add it to `rules/general.json` or `rules/product.json`, then regenerate the docs as [../AGENTS.md](../AGENTS.md) describes.

**A primary rule no hook can reach is marked.** A rule id whose detector no hook module reaches (its `OhMyRaspHooks` entry method is injected by no module) goes in the `not_wired` object of the JSON file that describes it, with the reason. Generated counts leave it out and `DETECTION-COVERAGE.md` lists it. `scripts/test_rule_cases.py` (`WiringTest`, reading the sources through `scripts/rule_wiring.py`) fails when a marked id becomes reachable or a rule nothing reaches is not marked, so wiring one in means taking it off the list in the same change.

**A rule has cases.** `rules/cases/<rule id>.toml` holds inputs for one rule id (the primary id, or the backport family when the primary has no counterpart) and what each engine does with each input today: `block`, `log`, `none` or `unreachable`, with a one-sentence `why` on every attack that is not blocked. The schema is the docstring of [`probes/common/rule_cases.py`](probes/common/rule_cases.py). The `rule-cases` probe starts one JVM per case with the packaged agent in block mode and fails when an engine does something else:

```bash
java-agent/scripts/check-agent.sh --line java8 rule-cases --file readFile_unwanted     # one file on one line
java-agent/scripts/check-agent.sh --line jdk25 rule-cases --case passwd-read-in-request  # one case by name
java-agent/scripts/check-agent.sh --line jdk25 rule-cases --file readFile_unwanted --print-actual
```

To add a case, write the input with any expectation, run its file with `--print-actual` on one primary and one backport line, paste the `[case.primary]` and `[case.backport]` tables it prints, and write the `why` of each attack that is not blocked. Record what the engines do, not what they should do: a difference between them is data, listed in [docs/RULE-CASES.md](docs/RULE-CASES.md#where-the-engines-differ). Every rule id in the catalogue is covered (an attack case that blocks or logs it, and a benign case in the same file) or listed with its reason in [`rules/cases/uncovered.toml`](rules/cases/uncovered.toml); `scripts/test_rule_cases.py` fails otherwise, and fails for a listed id that cases now cover. Regenerate the summary with `python3 java-agent/scripts/gen-rule-cases.py`.
